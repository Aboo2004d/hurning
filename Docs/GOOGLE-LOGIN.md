# تسجيل الدخول باستخدام Google خلف ngrok والاستضافة

## رابط العودة التلقائي حسب الدومين

لا يُثبت رابط ngrok أو hiring.ps في كود تسجيل الدخول أو إعداداته. يبني Google middleware الرابط المطلق من بروتوكول الطلب الحالي والدومين والمنفذ ومسار تثبيت التطبيق الحقيقي، ثم يضيف `/signin-google` دون اللغة. لذلك يتكيف التطبيق مع localhost وngrok ودومين الإنتاج تلقائيًا. خلف بروكسي موثوق تُستعاد HTTPS من ترويسات البروكسي أولًا.

يحتاج أي دومين جديد إلى تسجيل رابط عودته المسموح لدى Google Cloud؛ لا يستطيع التطبيق تسجيل دومينات جديدة تلقائيًا في Google ولا استخدام wildcard لتجاوز المطابقة.

## رابط العودة المسجل في Google Cloud

تحت APIs & Services ← Credentials ← عميل OAuth الخاص بالموقع ← Authorized redirect URIs:

- تجربة ngrok: `https://gusty-attentive-renewed.ngrok-free.dev/signin-google`
- الإنتاج: `https://hiring.ps/signin-google`
- إذا استُخدم localhost مباشرة، يلزم تسجيل رابط منفصل يطابق عنوانه وبروتوكوله ومنفذه، مثل `http://127.0.0.1:5186/signin-google`.

`/signin-google` رابط تقني دون `/ar` أو `/en`. ليست هذه صفحة الكنترولر التي يصل إليها المستخدم بعد اكتمال الدخول. تبدأ التجربة من الموقع على عنوان ngrok نفسه؛ لا تبدأ من localhost إذا كنت تريد العودة إلى ngrok. يجب أن يكون ClientId في التطبيق تابعًا لنفس عميل OAuth الذي أضيف إليه الرابط.

## تصحيح مسار العودة والبروتوكول

يضيف LanguagePathMiddleware اللغة مؤقتًا إلى Request.PathBase لتوليد روابط الصفحات. كان AuthenticationMiddleware يبدأ بعده، فيحفظ `/ar` أو `/en` ضمن OriginalPathBase. يعتمد Google على المسار المحفوظ لإنشاء redirect_uri وملف ارتباط correlation. لذلك تعديل PathBase داخل كنترولر Google بعد ذلك لا يصحح الأصل الذي حفظه المعالج.

بدأت المصادقة الآن قبل معالجة بادئة اللغة، بعد معالج الأخطاء. تبقى العودة المرئية إلى الكنترولر باللغة التي بدأ بها المستخدم. لا تلزم إضافة روابط `/ar/signin-google` أو `/en/signin-google` إلى Google.

يعمل UseForwardedHeaders مبكرًا قبل HTTPS redirects والمصادقة، لقراءة X-Forwarded-Proto وX-Forwarded-For من البروكسي الموثوق. يدعم ذلك ngrok المحلي الذي يتصل من loopback. لا تُقبل الترويسات من جميع عناوين الشبكة ولا تُمسح قائمة الجهات الموثوقة.

إذا كان بروكسي الاستضافة يتصل من عنوان غير loopback، أضف عنوانه الفعلي في إعدادات Web:

```json
{
  "ReverseProxy": {
    "KnownProxies": ["10.0.0.10"]
  }
}
```

العنوان في المثال توضيحي؛ يستخدم عنوان البروكسي الذي يتصل بالتطبيق، وليس عنوان الزائر أو اسم النطاق. يجب أن يرسل البروكسي بروتوكول الزائر الصحيح ويحافظ على Host العام. إذا لم يوجد بروكسي إضافي فلا حاجة لإضافة هذا القسم.

سُمح بنطاق `https://accounts.google.com` تحديدًا في CSP form-action بجانب الموقع وبوابة لحظة، لدعم تحويل نماذج المتابعة/الربط/اختبار Google. لم تتغير سياسة script-src.

## التجربة بعد التحديث

1. أعد تشغيل Web وافتح الموقع عبر عنوان ngrok الآمن، مثل `/ar` أو `/en`.
2. اضغط المتابعة باستخدام Google. يجب أن تظهر صفحة اختيار الحساب. إذا ظهر redirect_uri_mismatch، افتح تفاصيله وافحص redirect_uri؛ في تجربة ngrok يجب أن يساوي الرابط أعلاه تمامًا.
3. بعد اختيار الحساب، يدخل الحساب المرتبط والمفعّل إلى لوحة العضو. الحساب الجديد ينتقل لاستكمال بياناته والتحقق عبر تليجرام. إذا كان البريد مسجلًا مسبقًا دون ربط Google، يلزم الدخول بالطريقة الحالية ثم الربط من إعدادات العضو.
4. اختبار الإدارة التفاعلي في التكاملات يؤكد التفويض والعودة فقط؛ لا يثبت إنشاء العضوية أو تفعيل تليجرام أو كل مزايا الحساب.

## التحقق المحلي

الأمر `dotnet run --project tests/HiringPs.Checks -c Release -- --google-redirect-check` يشغل Google middleware الحقيقي مع HTTP مزود محاكى، دون حساب Google أو SQL أو مفاتيح حقيقية.

نجحت 65 حالة تحقق: العربية والإنجليزية، دومينات ngrok والإنتاج ودومين تجريبي بمنفذ مخصص، HTTP مباشر وHTTPS عبر بروكسي موثوق، جذر الموقع ومسار تثبيت فرعي، correlation cookie، وتطابق رابط العودة المستخدم في تبادل الرمز مع المرسل للتفويض، والعودة للغة الأصلية. تشمل الفحوص رفض بروتوكول مزور من بروكسي غير موثوق. نجح أيضًا بناء الحل و241 تحقق عضوية/واجهات. لم يُجرَ تسجيل دخول فعلي إلى Google أو قاعدة بيانات حية، ولا تلزم Migration لهذا الإصلاح.
