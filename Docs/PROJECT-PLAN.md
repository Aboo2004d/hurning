## 1. الهدف والقرارات الملزمة
منتج يعرض وظائف وفرص تدريب وعطاءات ومناقصات حديثة ودقيقة دون تكرار، مع تصنيف وبحث وفلاتر لكل نوع. المرحلة الأولى منتج قابل للنشر، وليس مجرد نموذج عرض.

| التصنيف الرئيسي | وظائف / تدريب / عطاءات / مناقصات؛ لا خلط بين نوع الفرصة ومجالها |

| الذكاء الاصطناعي | API سحابي يستدعى من .NET؛ اختبار مجاني قبل اختيار النموذج؛ لا دفع تلقائي |

| موعد الإطلاق | عند اكتمال المعايير والتحقق، دون تاريخ مفروض |

تطبيق الويب وعامل الجمع والخدمات المشتركة بلغة C#/.NET. المتصفح Chromium وdriver الخاص بـPlaywright متطلبات تشغيل محلية مسموحة؛ API النموذج سحابي. لا يلزم Python أو Crawl4AI. لا اشتراك جمع مدفوع معتمد؛ تبقى تجربة Firecrawl المجانية متاحة للمقارنة دون تغيير المسار الأساسي.
آخر تصحيح يلغي استبعاد التدريب والمناقصات، ويلغي اعتماد Microsoft Translator السابق. الواجهة تظل ثنائية اللغة؛ تبديل لغة الواجهة لا يترجم عنوان الإعلان أو ملخصه.
الموافقة السابقة على منع الإضافات أُلغيت بتوضيح المستخدم أن السيرفر Windows VPS وأن تثبيت المتطلبات مسموح. التخطيط لا يعني تثبيت أي شيء الآن؛ نتحقق من إصدار Windows ودعمه وصلاحيات حساب الخدمة قبل تشغيل Chromium.

## 2. نتيجة فحص المصادر
### 2.1 منهج الفحص وحدوده
- الفحص السابق كان مراجعة توثيق وصفحات عامة وطلبات HTTP محلية. نحفظ نتائجه كدليل اتصال أولي فقط؛ لا نعتمده اختبارًا كافيًا لمحرك جمع المواقع الحديثة.
- الفحص المطلوب الجديد: فتح المصدر في بيئة متصفح فعلية، تتبع تحميل المحتوى وطلبات البيانات والترقيم والتمرير، اختبار استخراج الإعلان بعد اكتماله، ثم قياس تشغيله بالمسار الإنتاجي المعتمد. لم يُنفذ هذا الفحص الشامل بعد، ولا نحول الدليل السابق إلى ادعاء نجاح أو فشل المتصفح.
- فحص صفحات القوائم، بعض التفاصيل، robots.txt، وشروط الاستخدام المتاحة.
- لم تستخدم بيانات دخول، ولم تُعطّل صلاحية شهادات HTTPS، ولم تُتجاوز صفحات الحماية.
- النتائج تخص مسار الشبكة وجهاز الفحص وتاريخ اليوم؛ ليست اختبارًا من IP استضافة Windows VPS.
- قراءة نتائج البحث لا تثبت قدرة HttpClient على جمع الصفحة؛ HTTP 200 لا يكفي دون وجود بيانات فعلية.
- لم ننفذ زحفًا شاملًا لكل الصفحات، أو اختبار جمع متعدد الأيام، أو تجربة AI بمفتاح حقيقي.
- غياب robots.txt أو سماحه بالزحف ليس ترخيصًا بإعادة استخدام النصوص. النشر يخضع لشروط المصدر وحقوق محتواه.

| ReliefWeb | API أعاد 403 بسبب appname غير معتمد | API مناسب جدًا لـ.NET بعد الاعتماد | مشروط بطلب اسم تطبيق واعتماده |

الهدف 3–5 مصادر ناجحة للإطلاق تغطي أنواع الفرص، ويمكن للمصدر الواحد تغطية عدة أنواع. الفحص السابق لم يختبر مصادر التدريب والعطاءات والمناقصات كمسارات مستقلة، ولا يثبت جاهزية المصادر لمحرك الجمع الديناميكي. يُستكمل الفحص بـPlaywright المحلي على Windows VPS؛ Firecrawl خيار مجاني احتياطي، ولا يجوز تغطيته ببيانات وهمية أو ادعاء شمول السوق.

### 2.5 ReliefWeb — مصدر ثالث مشروط
- [التوثيق](https://apidoc.reliefweb.int/) و[معامل appname](https://apidoc.reliefweb.int/parameters#appname).
- يوفر endpoint للوظائف وحقولًا للمكان والتصنيف والمتطلبات.
- من 1 نوفمبر 2025 يلزم اسم تطبيق معتمد مسبقًا. الطلب التجريبي باسم غير معتمد أعاد 403 برسالة صريحة.
- نجهز طلب الاعتماد للمستخدم دون إرساله باسم المستخدم تلقائيًا؛ لا يحتاج تثبيتًا على الاستضافة.
- بعد الموافقة نستخدم HttpClient وJSON، ونفحص حصة الطلبات الحالية، الترقيم، تاريخ التعديل والإغلاق.
- نختار مكان العمل أو التدريب الفعلي داخل فلسطين؛ لا يكفي ذكر فلسطين في النص. التدريب ضمن النطاق الجديد، ويحتاج فحص endpoint مخصص له؛ الوظائف الخارجية مؤجلة.
- الإذن باستخدام API لا يلغي حقوق أصحاب المحتوى؛ نعرض حقولًا وملخصًا قصيرًا ومصدرًا واضحًا ضمن الاستخدام المسموح.
- لم تُسترجع عينة وظائف ناجحة من API في هذا الفحص لعدم اعتماد الاسم.

### 2.6 Jobs.ps — غير جاهز للتفعيل
- [القائمة](https://www.jobs.ps/jobs)، [صفحة RSS](https://www.jobs.ps/rss)، [الشروط](https://www.jobs.ps/terms-of-use).
- /rss صفحة HTML تعرض روابط خلاصات، وليست feed XML نفسها. لم نتحقق من endpoint خلاصات يعمل من HttpClient.
- robots.txt أعاد 200، لكن القوائم والخلاصات أعادت 403.
- الشروط المتاحة عبر أداة القراءة تقصر الاستخدام على الشخصي غير التجاري وتقيد إعادة الإنتاج والنشر والتعديل والتخزين؛ لذلك يلزم مسار إذن مناسب للمشروع.
- لا نعتمد توليد ملخص 200 حرف كبديل مضمون للإذن، ولا نضمن أن RSS يعطي حقوق إعادة نشر.
- القرار: إبقاؤه في سجل المرشحين مع حالة AwaitingPermission/Access، وعدم بناء نجاح المرحلة الأولى على افتراض توفره.
- المتبقي بعد الإذن: feed الحقيقي، بياناته، شروط النسبة، وصول الاستضافة، ثم اختبار القوائم والتفاصيل.

### 2.7 الأونروا — احتياطي
- [بوابة الوظائف](https://www.unrwa.org/careers/vacancies).
- الجهة مصدر أصلي مهم، لكن صفحة الوظائف تشير إلى بوابات تقديم محلية ودولية؛ الصفحة التعريفية ليست قائمة وظائف جاهزة للجمع.
- الطلب المباشر أعاد 403. نتائج البحث تذكر Inspira، لكن لم يُثبت مسار قائمة وتفاصيل يعمل من .NET في هذا الفحص.
- لا نتجاوز قيود الدخول أو نفترض حل CAPTCHA. يمكن تجربة الوصول العام عبر Firecrawl ضمن الاختبار المعتمد؛ نجاحه لم يثبت بعد.
- يمكن استخدام وظائف الجهة الواردة في مصدر معتمد آخر مع حفظ المصدر ورابط التقديم الأصلي حيث يتوفر.
- التفعيل يحتاج قناة عامة قابلة للجمع، وشروط استخدام مناسبة، وعينة ناجحة من الاستضافة.

### 2.8 بوابة قبول كل مصدر
لا يصبح المصدر Active للنشر إلا بعد:
1. مراجعة شروط استخدام المحتوى وتوثيق السماح/نطاقه.
2. نجاح الطلب من الاستضافة نفسها مع HTTPS صحيح.
3. وجود بيانات كافية، ورابط أصلي، ومعرّف أو رابط ثابت.
4. اختبار القوائم والتفاصيل والترقيم وتعدد الوظائف.
5. اختبار إعادة التشغيل دون مضاعفة، والتحديث دون فقدان بيانات.
6. تحديد معدل طلبات وحدود صفحات مناسبين لكل مصدر.
7. مقارنة عينة يدويًا بالأصل، وتوثيق إصدار الموصل.
8. رفض الاستجابة الفارغة/صفحة الحماية حتى لو كان status=200.

## 3. المعمارية المعدلة — Windows VPS وعامل جمع مستقل
حل .NET واحد بمشروع Web MVC ومشروع Worker وخدمات عمل مشتركة. Worker يعمل كـWindows Service ويمتلك الجدولة وطابور المعالجة؛ الموقع يعرض البيانات ويديرها. التثبيت المحلي لـChromium وPlaywright أصبح مسموحًا. تعطيل IIS أو إعادة نشر الموقع لا يوقف العامل المستقل، بينما إعادة تشغيل VPS تتطلب استئناف العامل.

```text
Windows VPS / حل C# .NET
 ├─ Web MVC على IIS: قائمة / تفاصيل / بحث / أرشيف / إدارة / بلاغات
 ├─ Worker مستقل كـWindows Service
 │   ├─ BackgroundService: جدولة واستئناف وقفل SQL
 │   ├─ Playwright .NET + Chromium Headless محلي؛ API/RSS عند توفرهما
 │   ├─ موصلات: اكتشاف / انتظار محتوى / تفاصيل / ترقيم / تحديث
 │   └─ تنظيف / فحص / AI / تصنيف / تلخيص / منع تكرار / نشر
 └─ خدمات عمل مشتركة + EF Core → SQL Server والطابور الدائم
المحتوى بلغته الأصلية؛ لا Translation API
```

الأدوات بحسب مسؤوليتها، وليست قائمة بديل لمحرك المتصفح:
- IPageAcquisitionProvider يفصل تشغيل الصفحة عن تحليلها؛ ينتج محتوى بعد ظهور بيانات الإعلان مع رابط أصل وتوقيت وأدلة اكتمال.
- التنفيذ الأساسي: Microsoft.Playwright وChromium محلي داخل العامل؛ تحديد إصدار متوافق للمتصفح مع الحزمة، واختبار headless وتشغيل حساب الخدمة والوصول إلى مجلد المتصفح.
- Firecrawl عبر HTTPS خيار تجربة ومقارنة عند الحاجة، وBrowserless بديل إضافي غير معتمد للإنتاج؛ لا نستخدمهما لإخفاء عطل في تشغيل العامل المحلي ولا ندفع تلقائيًا.
- نبدأ بمتصفح واحد وتوازٍ منخفض، مع BrowserContext منفصل حسب المصدر؛ نغلق الصفحات والعمليات عند انتهاء الجولة ونقيس CPU وRAM وزمن التشغيل قبل زيادة التوازي.
- IHttpClientFactory يبقى وسيلة الاتصال بواجهات API والمزود، وSystem.Text.Json لقراءة النتائج؛ ليسا محرك تشغيل JavaScript.
- AngleSharp إن احتجناه يكون لتحليل HTML الناتج بعد العرض أو HTML مكتمل، لا لإنتاج محتوى ديناميكي بالانتظار.
- EF Core وIdentity وBackgroundService وSQL تبقى للبنية والحسابات والاستئناف؛ الاعتراض على الجمع لا يلغي هذه المسؤوليات.
- Resource files لنصوص الواجهة فقط؛ لا خدمة ترجمة ولا نص إعلان مترجم.
- نص أو Markdown منظف بعد تحميل المحتوى؛ لا توفير توكنز مضمون قبل قياس النصوص الفعلية.
- موصلات المصدر تجمع قواعد الانتظار والتفاعل والترقيم، مع AI للاستخراج والتصنيف وتلخيص 200 حرف وفحص بشري للحالات الملتبسة؛ لا ضمان أن رابطًا واحدًا يكفي لأي موقع بلا إعداد.

### 3.1 الجمع المحلي وحدود الاعتماد
المسار الأساسي يفتح المصدر بـPlaywright .NET داخل Worker على Windows VPS وينتظر اكتمال بيانات الإعلان. لا حاجة لسطح مكتب مرئي أو تشغيل المتصفح يدويًا، لكن إصدار النظام والصلاحيات يجب أن يدعما التشغيل headless.
قبل قبول المصدر نفحص القوائم والتفاصيل والتفاعل والترقيم والشروط، ونقارن الاستخراج بالأصل، ونوثق استهلاك الموارد. لا نجاح مضمون لمجرد تثبيت المتصفح؛ قيود الوصول و403 قد تستمر.
API/RSS خياران للمصادر التي توفر بيانات مناسبة. تجربة Firecrawl السابقة تبقى اختيارية للمقارنة ضمن المجاني؛ لم تعد البداية الإلزامية بعد تصحيح الاستضافة.
في المتصفح ننتظر selector/عدد العناصر/اكتمال طلب البيانات، لا networkidle أو تأخيرًا ثابتًا وحدهما. RSS/API الصحيحان يظلان مسارين جيدين حيث تتوفر البيانات، ولا يُلغيان لأسباب عمر التقنية.
طلبات 403 السابقة ليست دليلًا أن المتصفح سينجح أو أن المشكلة JavaScript فقط؛ الحماية والتراخيص والوصول مسائل مستقلة.

### 3.1.1 بروتوكول تجربة Firecrawl الاحتياطية
الحالة: تجربة مجانية موثّقة، اختيارية بعد اعتماد المسار المحلي على VPS؛ لم يُنشأ حساب/مفتاح ولم تنفذ طلبات Firecrawl فعلية.

1. إنشاء حساب مجاني واستخراج مفتاح API وحفظه سرّيًا على جهة الخادم؛ لا اشتراك مدفوع أو بطاقة أو تفعيل زيادة رصيد تلقائية ضمن التجربة.
2. تجربة ثلاثة مصادر مختلفة البنية: مصدر HTML/JSON مكتمل، ومصدر يحتاج JavaScript/تحميلًا متتابعًا، ومصدر تدريب أو عطاءات يضم روابط ملفات. الاختيار الفعلي بعد فحص الوصول وشروط المصدر.
3. عينة مقترحة: صفحة قائمة وعشر تفاصيل لكل مصدر، مع تكرار جلب بعض الصفحات واختبار تغيير وترقيم، ضمن حصة الحساب. المصدر المحجوب أو غير المسموح يسجل نتيجة ولا تستبدلها بادعاء نجاح.
4. استدعاء Firecrawl من .NET وإرجاع نص/Markdown منظف مع رابط الأصل وmetadata/status، أو HTML عند الحاجة. لا نفعّل استخراج JSON الذكي المدفوع إضافيًا افتراضيًا؛ نموذجنا يتولى التصنيف واستخراج الحقول والتلخيص.
5. ضبط انتظار المحتوى أو التفاعل عند الحاجة؛ لا نكتفي بمرور ثوانٍ أو وصول استجابة 200. التحقق من وجود الإعلان وروابط التفاصيل واكتمال النص جزء من النجاح.
6. ملفات PDF/الصور تُختبر كمسار مستقل؛ العثور على رابط الملف لا يثبت استخراج محتواه أو صحة OCR. نقارن خصوصًا الأرقام المرجعية والمواعيد بالأصل.
7. حفظ تقرير لكل طلب: المصدر والرابط، طريقة الجلب، الزمن، status، اكتمال المحتوى، الروابط المكتشفة، حجم النص، الرصيد الفعلي، والفشل وإعادة المحاولات. لا مفتاح API أو بيانات شخصية غير لازمة في السجل.
8. تكرار الاختبار على Windows VPS لاستدعاء HTTPS وقراءة النتائج؛ لا يكفي نجاحه محليًا. الخدمة الخلفية تستأنف من SQL وتمنع إعادة المعالجة دون تغيير المحتوى.
9. عند نقص الرصيد أو 429 نحفظ المهمة بحالة AwaitingCollectionQuota/RetryAt، مع backoff؛ لا نحول الصفحة الفارغة إلى نجاح أو الإعلان إلى منتهٍ.

معايير قبول التجربة:
- اكتشاف روابط القوائم والتفاصيل والترقيم فعليًا، ونص كامل يكفي للحقول والملخص؛ أي حقول حرجة ناقصة تُراجع ولا تُخمن.
- عينة يراجعها الأدمن بالمقارنة مع الأصل للأنواع الأربعة؛ لا رقم دقة تسويقي دون قياس.
- عدم مضاعفة الفرص عند إعادة الجولة، وعدم إعادة استدعاء AI لكل إعلان ثابت.
- تقدير استهلاك شهري من عدد صفحات القوائم والتفاصيل والتحديثات والمرفقات والجولات، لا عدد المواقع وحده.
- إذا تعثر مصدر بسبب التفاعل، تُقارن نفس العينة بـBrowserless المجاني عند توفر مفتاح، ثم يرفع القرار للمستخدم. لا افتراض أن البديل سيحل الحظر أو الحقوق.
- بعد التقرير فقط يقرر المستخدم اعتماد Firecrawl للإنتاج، تقليص عدد المصادر، أو مزودًا بديلًا أو ميزانية مدفوعة.

### 3.1.2 تصنيف الفرص وحقولها
- النوع الرئيسي OpportunityKind: Job / Training / Tender / ProcurementNotice. هذا تصنيف منتج، وليس حكمًا قانونيًا على نوع إجراء الشراء.
- Jobs: المسمى، الجهة، المدينة، الدوام، الخبرة، نمط العمل، الموعد.
- Training: عنوان البرنامج، الجهة، المكان/النمط، المدة، الفئة المستهدفة، الموعد، التكلفة إن وردت؛ لا نضع دوامًا وظيفيًا أو خبرة مختلقة.
- Tenders/ProcurementNotices: العنوان، الجهة الطارحة، الرقم المرجعي، مجال التوريد/الخدمة، مكان التنفيذ، مواعيد التسليم، شروط الأهلية والمرفقات إن توفرت.
- المراحل/الحصص lot identifiers والتعديل أو تمديد الموعد محفوظة؛ لا ندمج عطاءين لمجرد تشابه العنوان.
- نوع الفرصة فلتر عام، ثم فلاتر مرتبطة بالنوع. التدريب والعطاءات والمناقصات تظهر منذ المرحلة الأولى وفق النطاق المعدل.
- روابط العطاءات والوثائق مرجعية؛ لا تقديم عروض أو استقبال وثائق من المستخدمين داخل الموقع ضمن هذا النطاق.

### 3.2 الاستضافة والنشر
السيرفر Windows VPS والتثبيت مسموح. قبل إطلاق المرحلة الأولى نتحقق من:
- نجاح نشر MVC والاتصال بقاعدة البيانات وطلبات HTTPS الخارجية.
- صلاحيات الحساب على SQL، حجم القاعدة والتخزين وحدود الذاكرة وزمن الاستجابة.
- إصدار Windows المتوافق مع .NET 10 وPlaywright، ومعالج وRAM وتخزين VPS، وموقع SQL Server وترخيصه؛ لا نفترض أن ترخيص SQL Server الإنتاجي مشمول في VPS.
- تشغيل Web MVC عبر IIS بمتطلبات ASP.NET Core المناسبة، والعامل كـWindows Service منفصل يبدأ تلقائيًا مع recovery policy، ولا يتبع خمول IIS.
- حساب خدمة بصلاحيات محدودة، وصوله إلى المتصفح والمجلدات والأسرار وSQL، وعدم تشغيل Chromium كمسؤول دون حاجة.
- وسيلة حفظ الأسرار وData Protection keys في مكان دائم محمي خارج wwwroot.
- المهاجرات وفق تعديل المستخدم: الموقع يطبق MigrateAsync ثم SeedData تلقائيًا عند البدء. نحافظ على اتصاله وبياناته؛ لا حذف أو إعادة إنشاء قاعدة. قبل تحديث الإنتاج يلزم backup وصلاحيات schema المناسبة.
- نسخ قاعدة البيانات وملفات الحالة ومفاتيح Data Protection إلى وجهة خارج VPS واختبار الاستعادة، وتنبيه توقف الخدمة وامتلاء القرص.
يمكن تجهيز Hosting Bundle ومتطلبات المتصفح أثناء النشر بصلاحيات معتمدة. self-contained وحده لا يعوض ASP.NET Core Module المطلوب عند الاستضافة على IIS.

## 4. دورة حياة الجمع والمعالجة
### 4.1 البداية والاستئناف
- السيدر ينشئ إعدادات مفقودة فقط؛ لا يعيد NextDueAt أو حساب الأدمن أو حالة الطابور مع كل تشغيل.
- إعداد البداية المقترح: المصدر الجديد مستحق فور تفعيله، ثم دورة 24 ساعة.
- مدير خدمات Windows يبدأ Worker تلقائيًا؛ العامل يقرأ الجدول من SQL ولا يعتمد على بدء تطبيق الويب أو زياراته.
- إذا فاتت مواعيد أثناء توقف العامل/VPS تُنفذ جولة تعويضية واحدة، لا جولة لكل موعد فائت.
- تحفظ المواعيد بـUTC؛ العرض بتوقيت فلسطين. كل 8 ساعات مدة زمنية فعلية؛ تغير التوقيت الصيفي قد يغير ساعة العرض المحلية.
- بعد إتمام/إنهاء الجولة يحسب الاستحقاق القادم من الإيقاع المحفوظ مع تخطي المواعيد الماضية؛ فشل مصدر يستخدم RetryAt ولا يحوّل الجولة إلى نجاح كاذب.

### 4.2 جدولة مستقلة عن الموقع
Worker يعمل خارج IIS؛ توقف الموقع أو غياب الزيارات لا يوقف الجمع. تبدأ الخدمة مع النظام ويعاد تشغيلها بعد التعطل حسب سياسة recovery.
المواعيد كل 24 ساعة ثم كل 8 ساعات؛ إن توقف VPS أو تعطل SQL/العامل يبقى التنفيذ متأخرًا إلى حين التعافي، ويظهر ذلك في لوحة الحالة. لا وعد بزمن لحظي أو تشغيل لا يتعطل.
لا زر مطلوب لتفعيل الخدمة نفسها. يوجد زر جمع مستقل لكل مصدر عبر طابور SQL، دون Task.Run منفصل داخل Controller، والعامل يفحص الطلبات كل 5 ثوانٍ افتراضيًا.
الفحص والتعويض لا يعطلان فتح الصفحة؛ الخدمة تعالج دفعات صغيرة مع CancellationToken.

### 4.3 الاستمرارية ومنع التداخل
- قفل SQL من نوع sp_getapplock مرتبط بجلسة العامل يمنع الجولات المتزامنة ويُحرّر عند انقطاع الجلسة.
- لا تعقد transaction أثناء طلب الشبكة أو النموذج؛ تحفظ دفعة الصفحة ونقطة الاستكمال في معاملة قصيرة واحدة.
- العمليات قابلة للإعادة بقيود فريدة ونقاط استكمال محفوظة في SQL.
- حفظ تقدم الصفحات والعناصر أثناء العمل، لا انتظار StopAsync؛ قد لا يُستدعى عند توقف مفاجئ.
- فصل فشل مصدر عن غيره، مع backoff وحد محاولات، وتصنيف 403/429/TLS/تغيّر القالب.
- تقدم الاكتشاف يحدَّث بعد تخزين عناصر الطابور، لا بعد معالجة AI؛ نفاد الحصة لا يفقد الوظائف.

### 4.4 الجمع التزايدي
- أول مصدر: اجتياز كل الصفحات المتاحة ضمن حدود معقولة، وجمع المفتوح والموعد المجهول المرشح، لا كل التاريخ المنتهي.
- التشغيل التالي: قائمة الإعلانات + المعرّفات/الروابط المعروفة + نافذة تداخل.
- لا قاعدة «آخر 10» ولا توقف عند أول معروف إلا عندما يثبت ترتيب المصدر ومتانة الاكتشاف.
- التفاصيل المعروفة تُراجع دوريًا لرصد التعديل والتمديد؛ لا يمكن تجنب كل طلبات القديم وضمان تحديثه في آن واحد.
- لا يرسل للنموذج إلا المحتوى الجديد/المتغير بحسب content hash وإصدار المعالجة.
- دعم إعلان يضم وظائف متعددة: سجل الإعلان الخام واحد، وعدة فرص مع child key ثابت.
- مسؤولية كل موصل: اكتشاف، تفاصيل، ترقيم، تاريخ، حالة، وسياسة تحديث.

### 4.5 المعالجة والنشر
حالات مقترحة:
Discovered → ContentFetched → AwaitingAI → Validated → Ready → Published.
التفرعات: NeedsReview، DuplicateLinked، OutOfScope، RetryScheduled، SourceBlocked، Archived.

- تنتظر الوظيفة AI عند نفاد الحصة؛ لا تنشر بيانات مخمّنة.
- العنوان والملخص بلغة الإعلان الأصلية، ويحدَّد dir/lang للمحتوى مستقلًا عن الواجهة. لا انتظار ترجمة، ولا نص بديل مترجم تلقائيًا.
- الحقول الحرجة الغامضة أو تعارض الموعد أو الرابط أو دمج محتمل خاطئ تُراجع قبل النشر.
- الفرص اليدوية تمر بتحقق ونسخة سجل؛ الأدمن يستطيع كتابة ملخص بلغة الأصل دون الاعتماد على AI.
- حظر إعادة إدراج الوظائف التي أخفاها الأدمن تلقائيًا؛ حفظ قرار override منفصل عن المصدر.

## 5. البيانات والبحث والتكرار
### 5.1 الجداول الأساسية
| المجموعة | الجداول/المسؤولية |
|---|---|
| المصادر | Sources، SourceConfigurationVersions، ConnectorType/Version، حالة الإذن والوصول |
| المحتوى | SourceItems، SourceItemVersions، ExternalId، ChildKey، ContentHash، رابط المصدر، آخر تحقق |
| الفرص | Opportunities، OpportunityKind، OriginalLanguage، OriginalTitle، Summary؛ تفاصيل JobDetails / TrainingDetails / TenderDetails حسب النوع |
| المصدر والروابط | OpportunitySourceLinks، رابط الإعلان والتقديم/وثائق العطاء؛ لا جدول ترجمات |
| المكان | Locations، OpportunityLocations لدعم عدة مدن؛ منطقة/مدينة دون اختراع مكان غير منشور |
| المعالجة | ProcessingQueue، ProcessingAttempts، PromptVersion، Provider/Model، حصص واستهلاك |
| التشغيل | SchedulerState، WorkerLeases، ScrapeRuns، SourceRunLogs، checkpoints |
| المراجعة | ReviewItems، DuplicateDecisions، AdminAuditLog، UserReports |
| المرحلة 3 | Identity users، SavedJobs، SavedSearches، AlertPreferences، EmailOutbox، DeliveryLogs |
| المرحلة 4 | Plans، Subscriptions، PaymentEvents، Entitlements عند اختيار وسيلة الدفع |

حقول الوظيفة تفرق بين SourcePublishedAt وFirstSeenAt وLastSeenAt وLastVerifiedAt وModifiedAt.
Deadline قد يكون null؛ مصدر الموعد وإثبات الانتهاء محفوظان.
تخزين نص داخلي للمراجعة ضمن حقوق المصدر وسياسة الاحتفاظ، لا عرض صفحة HTML الأصلية أو سكربتاتها.
تخزين raw payload ضروري لفحص الأخطاء، لكن احتفاظ محدود قابل للضبط وتنقيح ما لا يلزم؛ لا تخزين بيانات المتقدمين.

### 5.2 القيود
- قيد فريد على SourceId + ExternalId + ChildKey، أو معرف مشتق موثق عند غياب المعرف.
- حفظ ملخص أصل واحد مرتبط بإصدار المحتوى؛ لا قيود أو سجل Translation.
- معالجة محفوظة حسب SourceItemVersion + ProcessingVersion لمنع تكرار الاستدعاء غير الضروري.
- RowVersion للتعديل المتزامن؛ فهارس على الحالة والمكان والتصنيف والمواعيد.
- لا يجعل URL مختلف دليلًا على فرصة مختلفة؛ ولا يجعل عنوان/جهة متماثلين دليلًا كافيًا للدمج.

### 5.3 منع التكرار
1. مطابقة داخل المصدر بالمعرف والرابط وإصدار المحتوى.
2. مطابقة مؤكدة بين المصادر بمعرف الجهة/الوظيفة أو رابط تقديم محدد.
3. اختيار مرشحين من نفس نوع الفرصة النشطة وأرشيف قريب حسب الجهة والعنوان والمكان والموعد والرقم المرجعي إن وجد؛ ليست نافذة 48 ساعة فقط. لا دمج وظيفة مع تدريب أو إعلان شراء، وتفصل تعديلات/حصص العطاء عن الإجراءات الجديدة.
4. مقارنة نصية وتطبيع عربي/إنجليزي، ثم AI عند الحاجة.
5. قرار ملتبس يذهب للمراجعة؛ منع الدمج الخاطئ أهم من إجبار كل تطابق على الدمج.
6. دمج مؤكد يبقي سجل وظيفة واحدًا وروابط جميع المصادر، مع أصل كل معلومة وإمكانية فصل دمج خاطئ.
إعادة إعلان نفس المسمى قد تكون شاغرًا جديدًا، وإعلان واحد قد يضم عدة مواقع/وظائف؛ لا تختزلها دون دليل.

### 5.4 البحث والفلاتر
- نص العنوان والجهة والملخص بلغته الأصلية؛ نوع الفرصة والمدينة والمجال. الدوام والخبرة للوظائف فقط، والحقول الخاصة بالتدريب والعطاءات تظهر بحسب النوع.
- القيم غير المعروفة تظهر كغير محددة، لا تخمين من النموذج.
- البحث بالعربية والإنجليزية مع أسماء بديلة للمدن والمجالات وتطبيع للبحث فقط؛ النص المعروض يبقى أصليًا.
- ترتيب افتراضي بالأحدث بحسب نشر موثوق ثم أول رصد، مع بيان الفرق.
- pagination من SQL؛ لا تحميل كل الوظائف إلى المتصفح.
- نوع الدوام مستقل عن نمط العمل وعن أهلية التقديم.
- البحث الأساسي بـSQL والفهارس؛ Full-Text Search خيار لاحق فقط إن كان متاحًا، لا تثبيت محرك خارجي.

## 6. AI ولغة المحتوى والحصص
### 6.1 اختبار النموذج قبل الاعتماد
لا يوجد مفتاح AI لدى المستخدم؛ الاختبار الفعلي مؤجل حتى إنشاء الحساب.
المرشحان الأوليان Gemini Flash-Lite وGPT-OSS 20B عبر Groq؛ اسم النموذج والأسعار وإتاحته للمنطقة تتحقق يوم الاختبار.
نستخدم نفس عينة من 50 إعلانًا متنوعًا تغطي الوظائف والتدريب والعطاءات والمناقصات، بعد توفر محتوى مسموح استخدامه، مع إجابات مرجعية يراجعها الإنسان.
نقيس: الحقول الحرجة، الموعد، الوظائف المتعددة، الاستبعاد، JSON، الملخص، التكرار، معدل الفشل، والتوكنز الفعلية.
الحصة المجانية/حدودها ليست ضمان توفر دائم، ولا اشتراك تطبيق المحادثة بديلًا لفوترة API.
لا نعتبر طلب JSON ضمانًا للصحة. Schema وتحقيق أنواع وقيم وقواعد إلزامية في C#.
يطلب دليلًا نصيًا للحقول الحساسة؛ «ثقة النموذج» وحدها ليست أساس نشر.
المحتوى المسحوب بيانات غير موثوقة، لا تعليمات للنموذج؛ لا تنفيذ أدوات أو روابط يختلقها النص.

### 6.2 حد 200 حرف
- ملخص بلغة الأصل يُنشأ من المهام والمتطلبات الأهم؛ لا حشو للجهة والمكان المعروضين أصلًا إلا عند ضرورة.
- قياس موحد بـStringInfo/grapheme clusters، شامل المسافات وعلامات الترقيم، لملخص الإعلان بلغته الأصلية.
- لا قطع عشوائي يغيّر معنى شرط أو يقطع كلمة. محاولة إعادة صياغة محدودة أو قالب حقائقي قصير؛ إن تعذر يحال للمراجعة.
- النموذج يختصر فقط ولا يترجم؛ العناوين وأسماء الجهات لا يعاد صياغتها بما يغير المعنى. الإعلان متعدد اللغات يحتفظ بالمحتوى الوارد فعليًا، دون إنشاء ترجمة جديدة.
- الملخص لا يغني عن النص الأصلي لشروط الأهلية والتقديم؛ علامة ملخص آلي ورابط المصدر.
- لا يترجم اسم الشركة أو الرابط أو البريد والموعد إلى قيمة مخمّنة.

### 6.3 إلغاء ترجمة المحتوى
لا Microsoft Translator ولا Google Translation ولا ترجمة بالنموذج، ولا مفاتيح أو حصص أو طابور ترجمة.
نصوص الواجهة وقيم التصنيفات ثابتة بالعربية والإنجليزية عبر الموارد. لغة الإعلان وملخصه لا تتغير بتبديل الواجهة.
حدود AI تختلف حسب المزود؛ عند نفادها تحفظ العناصر في الطابور حتى تجددها دون دفع تلقائي. خدمة المتصفح إن اعتمدت تحتاج سياسة حصة منفصلة يوافق عليها المستخدم، ولا نفترض أنها مجانية أو تغطي جميع المصادر.

## 7. صفحات المرحلة الأولى والأمان
### 7.1 الصفحات
- قائمة فرص وبحث وفلاتر وروابط قابلة للمشاركة، مع أقسام وظائف / تدريب / عطاءات / مناقصات واضحة.
- تفاصيل بحسب النوع: عنوان وجهة ومكان وملخص بلغة الأصل وموعد ومصدر؛ الدوام والخبرة للوظيفة، المدة والفئة للتدريب، الرقم المرجعي ومجال التوريد ومواعيد العطاء ومرجع الوثائق للمشتريات.
- أرشيف مع علامة انتهاء واضحة، دون تقديم داخلي.
- نموذج إبلاغ: منتهية، مكررة، بيانات خاطئة، رابط معطل، سبب آخر.
- لوحة أدمن: المصادر وإعداداتها، الوظائف اليدوية، مراجعة الالتباس، البلاغات، نتائج الجمع والطابور والحصص.
- لا يتطلب التصفح أو الإبلاغ حساب باحث في المرحلة الأولى.

### 7.2 قواعد مهمة
- لا نحذف إعلانًا بسبب 403/404/انقطاع واحد؛ تعطل المصدر ليس إثبات انتهاء الشاغر.
- إثبات انتهاء: موعد موثوق مرّ، تصريح بإغلاق/إلغاء من المصدر، أو قرار أدمن موثق بعد التحقق.
- المصدر دون موعد يبقى ظاهرًا مع LastVerifiedAt؛ تنبيه داخلي للتقادم لا أرشفة تلقائية.
- فصل رابط الإعلان عن رابط التقديم؛ إذا التقديم هاتف/بريد لا نخترع applyUrl.
- العناوين والملخصات encoded؛ لا عرض HTML خام أو سكربتات المصادر.

### 7.3 الحماية
- الأدمن بـIdentity، وSeedData الخاص بالمستخدم محفوظ دون تعديل. قبل النشر العام تُغيّر كلمة المرور الأولية عبر شاشة الحساب؛ لا تُعرض قيمتها في التوثيق.
- أسرار AI/SQL/Firecrawl خارج الشيفرة وJavaScript وملفات إعداد عامة؛ خيارات استضافة آمنة ومراجعة قبل النشر.
- حماية CSRF، rate limiting للبلاغات، صلاحيات الإدارة، سجل تعديل دون أسرار.
- إدارة مصادر الجمع تتضمن SSRF protection: HTTPS ونطاقات مسموحة، منع عناوين داخلية/metadata/loopback وإعادة فحص redirects.
- لا تنفيذ سكربتات المصدر داخل موقعنا أو عرضه خامًا للمستخدم. التنفيذ داخل متصفح جمع معزول فقط إن اعتمد؛ إعدادات المصدر لا تتيح أوامر عامة على السيرفر أو تشغيل كود يقدمه الزائر.
- timeouts وحد حجم الاستجابة والتوازي؛ مبدئيًا مصدر واحد/عدد قليل مع قياس الذاكرة.
- نسخ احتياطي، سياسة خصوصية وشروط استخدام وطلب إزالة محتوى وقناة تواصل.
- SEO من حقائق محفوظة فقط؛ لا JobPosting structured data غير مكتمل أو مضلل، ولا وصف يغطي شروطًا غير موجودة في الصفحة.

## 8. مراحل التنفيذ ومعايير القبول
### المرحلة الأولى — منتج قابل للنشر
#### الأعمال بالترتيب
1. تثبيت هذه الوثيقة، ثم قرار التصميم الأساسي دون إضافة نطاق وظيفي.
2. فحص Windows VPS ومواصفاته، وتجهيز .NET/IIS والعامل المستقل وChromium وSQL والأسرار والنسخ الاحتياطي.
3. اختبار Playwright .NET المحلي على المصادر والأنواع الأربعة، وقياس الموارد؛ Firecrawl المجاني للمقارنة عند الحاجة وليس شرطًا لاعتماد المحرك المحلي.
4. إنشاء الحساب الإداري والموديل والمهاجرات والقيود والطابور.
5. تنفيذ خدمة الاستئناف والـlease والجدولة اليومية مع اختبار التوقف.
6. تنفيذ الجمع الأول والتزايدي ومراجعة التحديثات والتعدد.
7. اختبار AI المجاني واختيار النموذج؛ التصنيف والتلخيص والتحقق والتكرار والمراجعة.
8. تنفيذ عرض المحتوى بلغته الأصلية مع ملخص 200 حرف؛ اختبار الاتجاه واللغة منفصلين عن لغة الواجهة، وتصنيفات الأنواع وحقولها.
9. بناء الموقع العام والأرشيف والبلاغات ولوحة الإدارة.
10. اختبار متكامل بعينة حقيقية، ثم اختبار على الاستضافة ونشر واستعادة.

اختبارات مطلوبة للسلوك المعقد، لا اختبارات شكلية تعيد كتابة التنفيذ:
- fixtures مسموحة للقوائم والتفاصيل وJSON وترقيم المصادر.
- نفس المصدر مرتين، تغيير deadline، عدة شواغر، ترتيب غير ثابت، صفحة فارغة وحماية 200.
- اختبارات SQL حقيقية للقيود الفريدة والlease والتزامن والاستئناف.
- وقف التطبيق منتصف دفعة، انتهاء lease، فشل بعد استجابة AI وقبل الحفظ، وإعادة المحاولة.
- فحص يدوي مرجعي للحقول والتلخيص بلغة الأصل والتكرار وتصنيف الأنواع؛ اختبار قائمة ديناميكية وترقيمها وانتظار اكتمالها وفق المحرك المعتمد.
- نفاد الحصص، 429، TLS، 403، وتراجع حجم النتائج.
- تجربة واجهة عربية/إنجليزية وهاتف، روابط المصدر والتقديم والبلاغات.
- تحقق نشر من Windows VPS، لا استنتاجه من جهاز التطوير.

المؤشرات: LastSuccessfulDiscovery، LastSuccessfulProcessing، زمن الجولة، مصدر معطل، جديد/متغير/مكرر/مراجع، عمر انتظار AI، آخر تحقق، استهلاك ومعدل فشل؛ واستهلاك جلسات محرك الجمع إن اعتمد.
نفرّق بين جمع ناجح ومعالجة متأخرة؛ رسالة «محدّث» لا تستخدم إذا المحتوى ينتظر منذ مدة.
لوحة الحالة المصدر الأساسي للمراقبة في المرحلة الأولى؛ إرسال تنبيهات إدارية بالبريد ليس مطلبًا مثبتًا الآن.

## 10. التكلفة وترتيب العمل
- استخدام الاستضافة الحالية لا يجعل تكلفة المشروع صفرًا؛ حسابها الحالي/تجديدها والقاعدة والنسخ الاحتياطي تبقى بنودًا.
- AI يبدأ بحصة مجانية دون ترقية؛ Firecrawl تجربة مجانية اختيارية. الجمع الأساسي محلي وتكلفته موارد VPS وصيانة المتصفح، ولا تكلفة ترجمة. أي اشتراك جمع مدفوع يحتاج موافقة؛ البريد والأسعار تؤجل حتى اختيار المزود.
- بحسب [تسعير Firecrawl الرسمي](https://www.firecrawl.dev/pricing) الذي روجع في 11 أكتوبر 2026: المجاني 1,000 رصيد شهريًا دون بطاقة، والجمع الأساسي رصيد لكل صفحة؛ JSON/ميزات متقدمة والتفاعل قد تستهلك أكثر. خطة Hobby المعروضة 19 دولارًا بفوترة شهرية أو ما يعادل 16 دولارًا شهريًا بفوترة سنوية مقابل 5,000 رصيد، وهذه أرقام مقارنة وليست موافقة شراء؛ يعاد التحقق عند التسجيل.
- الحصة لا تعني 1,000 إعلان جديد: صفحات القوائم والترقيم والتفاصيل والمراجعات والملفات قد تستهلك منها. صفحة خطأ 403/404 مع نتيجة قد تُحتسب بحسب سياسة المزود.
- مثال قياس فقط: 30 مصدرًا × 3 جولات يوميًا × 30 يومًا = 2,700 فحص قائمة قبل التفاصيل؛ لذلك لا وعد بكفاية المجاني لتغطية 20–30 مصدرًا. نتوقف عند حد الحساب بدل الدفع التلقائي.
- الطلبات للنموذج = الإعلانات الجديدة والمتغيرة + الحالات الملتبسة + إعادة المحاولات، لا عدد زيارات المستخدمين.
- لا إعادة معالجة للنص الثابت عند كل زيارة، ولا ترجمة للمحتوى ضمن النسخة المعدلة.
- التشغيل ثلاث مرات يزيد HTTP ووقت التشغيل، ولا يضاعف تكلفة كل إعلان ثابت ثلاثًا تلقائيًا.
- صيانة المصادر ووقت المراجعة وتطوير الاختبارات تكلفة حقيقية.
- لا ميزانية مدفوعة معتمدة، ولا تقدير 99% هامش ربح، ولا وعد شهري 1–3 دولارات قبل قياس العينة.
- لا موعد إطلاق ثابت. تقدير جهد المرحلة الأولى يصدر بعد اختبار المصدر والنموذج والاستضافة، لأن الموافقات الخارجية قد تطيل المدة دون جهد برمجي مكافئ.

المسار الحرج: فحص وتجهيز Windows VPS → Worker وPlaywright محلي → قبول المصادر والأنواع الأربعة → نموذج مختبر → تحقق وتكرار وتصنيف → واجهة وإدارة → اختبار نشر وتعافٍ.
يمكن تنفيذ الهيكل والواجهة بالتوازي المنطقي مع انتظار الموافقات، لكن لا إعلان اكتمال التكامل بالبيانات التجريبية.

ما كان جيدًا عند Gemini: فصل العرض عن الجمع، البدء بمصادر قليلة، استخدام API للنموذج بدل جهاز يعمل دائمًا، التطبيع، السحب التزايدي، ولوحة المصادر. احتفظنا بهذه الأفكار، وأضفنا القيود والاختبارات التي تجعلها خطة قابلة للتنفيذ.

تصحيح لتقديراتنا السابقة أيضًا: اقتراحنا الأول للمصادر كان مبدئيًا؛ الفحص السابق أثبت شرط appname وعوائق الطلب المباشر وشهادة www في PalCareer فقط. قصر الحل على HttpClient وAngleSharp لم يلبّ طلب المستخدم دعم جمع المواقع الحديثة، لذلك أزيل من صفة المعمارية النهائية ووُضع قرار المتصفح صراحة. الأدوات نفسها ليست منتهية الصلاحية؛ الخطأ في اعتبارها وحدها تغطية كاملة دون تشغيل JS حيث يلزم.

تغييرات نطاق من المستخدم وليست أخطاء تاريخية لـGemini: إدخال التدريب والعطاءات والمناقصات الآن يلغي قرار استبعادها السابق، وإلغاء ترجمة المحتوى يلغي اعتماد Microsoft السابق. لا نلوم Gemini على شروط أو قرارات استجدت لاحقًا، ولا نعتمد مزود متصفح أو تكلفة قبل موافقة المستخدم.

آخر تصحيح للبنية التحتية: السيرفر Windows VPS وليس استضافة مقيدة بلوحة SolidCP، وتثبيت متطلبات الجمع مسموح صراحة. لذلك استُبدلت خدمة الجمع داخل موقع الويب بعامل .NET مستقل، وأصبح Playwright/Chromium المحلي الاتجاه الأساسي. تحفظ النسخة السابقة في PROJECT-PLAN.before-vps.md؛ لا تعتبر نتيجة فحص محلي سابقة اختبارًا للـVPS أو للمتصفح المحلي.
