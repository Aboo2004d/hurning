# تشغيل العضوية والباقات وتليجرام

تحديث: 18 أكتوبر 2026. المرجع الوظيفي: [MEMBERSHIP-PLAN.md](MEMBERSHIP-PLAN.md).

## حالة هذه الدفعة

أُضيفت مناطق Admin وMember، مسارات اللغة، صفحات الحساب والعضوية والإدارة، نماذج الاشتراك والطلب والمراجعة والخصم، وطبقة تحقق تليجرام وطابور الرسائل. هذه إضافة كبيرة تحتاج تجربة SQL Server وتليجرام على بيئة المستخدم قبل النشر الفعلي. بناء الكود وفحوص HTTP دون قاعدة بيانات لا تثبت سلامة كل المعاملات على قاعدة حية.

**تحديث الربط:** أضيف موصل لحظة لإنشاء الدفع والتحقق من API واستقبال Webhook الموقّع بناءً على التوثيق الذي أرسله المستخدم. أُعد بوت `PalestineEmploymentBot` ورابط ngrok واللغتان، وتبقى المفاتيح `***`. لا توجد عملية حقيقية مجرّبة هنا؛ أُضيف موصل جوال باي وOTP وSandbox؛ تفاصيله موثّقة في [JAWWAL-PAY.md](JAWWAL-PAY.md). راجع [دليل لحظة وتليجرام](LAHZA-TELEGRAM-LOCAL.md) للخطوات الحالية والتجربة والاستضافة.

فُصلت إجراءات الإدارة القديمة أيضًا إلى Controllers بحسب المسؤولية: المصادر والفرص والرسائل والصفحات والتشخيص وAI والأدوات وغيرها، مع قاعدة مشتركة للحماية والمساعدات. AdminActionRoutes يحافظ على الروابط السابقة دون إبقاء Controller شامل لكل الصفحات.

## الملفات والإعدادات

كل الإعدادات الجديدة في `src/HiringPs.Web/appsettings.json` و`src/HiringPs.Worker/appsettings.json` بالطريقة التقليدية المطلوبة. القيم السرية الافتراضية `***`؛ الرايتان مفعّلتان للتحضير لكن الاتصال يبقى غير جاهز دون الرموز الصحيحة:

راجع أقسام JSON الحالية في ملفي التطبيق؛ إعدادات الدفع مقسمة إلى `Sandbox` و`Production` داخل الملف نفسه. اختيارها تلقائي حسب بيئة .NET، كما هو موضح في [PAYMENT-ENVIRONMENTS.md](PAYMENT-ENVIRONMENTS.md).

القيم السرية تبقى `***`: تليجرام BotToken/WebhookSecret، ولحظة SecretKey لكل بيئة، وجوال باي ApiKey لكل بيئة. ترويسة الشريك ثابتة `X-Partner-Key`.

- يستبدل المسؤول `***` محليًا/على الاستضافة. لا ترفع القيم الحقيقية إلى GitHub.
- نفس بيانات البوت مطلوبة في Web وWorker. `BotUsername` دون `@`، و`WebhookSecret` قيمة عشوائية طويلة لا تقل عن 24 حرفًا صالحة لـTelegram secret_token.
- يُضبط `Seo:PublicOrigin` على أصل الموقع HTTPS الصحيح في المشروعين؛ العامل يستخدمه لروابط الرسائل. القيمة الاحتياطية الحالية `https://hiring.ps`.
- ملفات الإثبات صور PNG/JPEG اختيارية حتى 5 MB، خارج wwwroot. المسار النسبي محسوب من مجلد تشغيل Web؛ يُفضل مسار بيانات دائم خارج مجلد publish على الاستضافة حتى لا تُفقد الأدلة عند استبدال ملفات النشر. امنح حساب Web حق القراءة والكتابة عليه. الروابط تتطلب صاحب العملية أو Admin، والتنزيل دون تخزين مؤقت.
- لا تغيير في أدوات PDF أو مسارات Chromium ضمن هذه الدفعة، ولا يلزم تثبيت مكتبة بوت إضافية؛ الاستدعاء عبر HttpClient.

## قاعدة البيانات والروابط

- Migration جديدة باسم `MemberSubscriptionsAndTelegram`؛ Web يطبق migrations عند بدء التشغيل وفق السلوك الموجود أصلًا. خذ نسخة احتياطية لقاعدة بيئة التجربة قبل تطبيقها، ولا تختبر على بيانات مالية حقيقية مباشرة.
- المستخدم الإداري الحالي وIdentity والجداول القديمة باقية. لم تُنشأ باقة مدفوعة تلقائيًا ولم يُحوَّل أي زائر قديم إلى اشتراك.
- إتاحة التفاصيل للعامة مفعلة لكل الأنواع في البداية للحفاظ على العرض الحالي. تغيّرها الإدارة من الباقات ← إتاحة الأنواع.
- المنشورات الموجودة عند الترقية تُسجل كمنشورات تاريخية مكتملة، لمنع إرسال جميع الإعلانات القديمة عند تشغيل التنبيهات.
- `/ar` و`/en` لغة صريحة لها الأولوية؛ اللغة المفقودة أو المخطوءة تعاد إلى الكوكي ثم المتصفح ثم العربية. لا تُفقد بقية المسارات أو query.
- الروابط السابقة مثل `/Home/Contact` و`/Home/Details/123` ما زالت مدعومة بعد إضافة بادئة اللغة. الروابط الجديدة للتفاصيل `/ar/Opportunities/Details/123`.
- سجل كل عملية شراء مستقل ماليًا؛ تجمع الواجهة التجديدات المتجاورة من نفس إصدار الباقة لعرض المدة المتبقية كاملة، دون تغيير الصفوف المالية.

## تشغيل تليجرام محليًا

1. أنشئ البوت من BotFather واضبط اسمه ومفتاحه وWebhookSecret في ملفي الإعدادات.
2. يلزم عنوان HTTPS عام يصل إلى Web لاستقبال webhook على `/integrations/telegram`. `localhost` وحده لا يستقبل رسائل Telegram. استخدم بيئة تجريبية عامة أو نفق تطوير معتمد لديك؛ لا تضع هذا المسار خلف تسجيل دخول.
3. سجّل webhook لدى Bot API بالطريقة الرسمية `setWebhook`، مع `url` للعنوان المذكور و`secret_token` المطابق و`allowed_updates=["message"]`. لا تُطبع قيمة BotToken في سجل تشغيل مشترك.
4. اجعل `Telegram:Enabled=true` في Web وWorker وأعد تشغيلهما. لا تشغّل webhook وpolling آخر لنفس البوت بالتزامن؛ التنفيذ الحالي webhook فقط.
5. شغّل سكربت التشغيل المحلي المعتاد. Web يحفظ رسائل webhook في SQL ويؤكد استلامها؛ Worker يعالجها مستقلًا عن جولات الجمع.
6. جرّب التسجيل: رقم دولي، افتح الرابط الخاص من الموقع، شارك رقمك الخاص بزر البوت، أدخل الرمز. النص اليدوي أو contact لشخص آخر لا يثبت ملكية الرقم.
7. جرّب استعادة كلمة المرور، إيقاف التنبيهات، إعادة التفعيل برمز، وتغيير الربط عبر التحقق من القديم ثم الجديد.

الرمز 6 أرقام، صالح 5 دقائق، حتى 5 محاولات للرمز، وإعادة الطلب بعد دقيقة ضمن الغرض نفسه. رابط الربط الأولي صالح 15 دقيقة. رموز الإكمال للاستراد/تغيير الربط محدودة بوقت وحالة محفوظة في الخادم. الاستعادة الإدارية تعطي رابط ربط سريًا يعرض مرة في لوحة الإدارة بعد توثيق تحقق الهوية؛ لا يُنشر الرابط.

## أوامر البوت

- `/start`: الربط من رابط الموقع، أو حالة الحساب للمرتبط.
- `/status`: الباقة الحالية والانتهاء وحالة التنبيهات.
- `/stop`: إيقاف تنبيهات الفرص والمحفوظات فقط؛ تستمر رسائل الدفع والحساب والتحقق.
- `/help`: الأوامر وأزرار باقتي وتفضيلاتي.
- `/payment_status orderId`: تحقق من عملية تخص الحساب المرتبط، وحد الاستعلام 30 ثانية لكل عملية. يحفظ السيرفر نتيجة التحقق والاشتراك قبل الرد إلى البوت.

إعادة تفعيل التنبيهات من لوحة المستخدم برمز يرسله البوت، وليست بأمر غير موثق يتجاوز التحقق.

## إدارة الباقات والدفع

- أنشئ باقة بأسماء ووصف AR/EN وسعر ILS وعدد أيام، وحدد تفاصيل/تنبيهات كل نوع مستقلًا. تعديلها ينشئ إصدارًا جديدًا؛ لا يعدّل المزايا المشتراة.
- الباقات المختلفة تُضاف لنهاية التسلسل؛ التجديد المتصل لنفس الإصدار يظهر كمدة واحدة للمستخدم. لا تجديد أو خصم تلقائي من البطاقة.
- الخصم الكامل يتيح اختبار دورة طلب حقيقية داخل النظام دون بوابة خارجية. يلزم قبول شروط عدم الاسترداد حتى للطلب ذي المبلغ الصفري، ويُحفظ الطلب.
- كود الخصم يُحجز عند إنشاء الطلب، بما فيه الطلب الذي قد يتأخر تأكيده؛ الحجز يستهلك حد الكود ومرة المستخدم ولا يُحرر تلقائيًا عند الفشل. هذه آلية تحفظ الحدود مع التأكيد المتأخر؛ يجب مراجعة سياسة إعادة استخدام الكود للطلبات غير المدفوعة قبل إطلاق الدفع الحقيقي.
- مهلة بدء الدفع 10 دقائق؛ انتهاء المهلة لا يرفض دفعًا ثبت نجاحه لدى المزود لاحقًا. إعادة المحاولة تنشئ طلبًا مستقلًا.
- الإدارة تستعلم أو تعتمد يدويًا مع سبب وإثبات، ويتسجل الفاعل والتاريخ. التأكيد اللاحق لنفس الطلب لا يمنح مدة ثانية.
- مراجعة المستخدم ترتبط بالطلب، والصورة والملاحظة اختياريتان؛ يحلها Admin بنتيجة وسبب يرسلان عبر تليجرام.
- صفحة بوابات الدفع تفصل زر التفعيل الإداري عن جاهزية الموصل والإعدادات؛ التفعيل وحده لا يسمح بالدفع. جوال باي مخفية من قائمة المدفوعات المختصرة ما دامت معطلة بالإعدادات.

أضيفت مسارات استقبال Webhook لحظة وصفحة العودة وموصل API الرسمي الموثق. التنفيذ يمنع تكرار بدء العملية، ويطابق المرجع والمبلغ وILS ووضع Test/Live، ويقصر رابط checkout على `https://checkout.lahza.io`. تسجيل التوقيع الحي وتجارب API الفعلية ما زالت مطلوبة. راجع [الدليل الحالي](LAHZA-TELEGRAM-LOCAL.md).

## تنبيهات العامل والإدارة

- `MembershipWorker` خدمة خلفية منفصلة عن جولات الجمع، تعمل كل 5 ثوانٍ؛ فحص المدفوعات مستقل عن جاهزية البوت، بينما مهام تليجرام تبدأ عندما يجهز. تنفذ دفعات محدودة مع lease في SQL؛ توقف الموقع لا يمحو طابور الإرسال.
- حدث النشر يُحفظ مع التغيير نفسه، ثم يوسع العامل الجمهور على دفعات؛ لا يعتمد على آخر عدد ثابت من الإعلانات.
- تتطابق الأنواع والمجال والموقع، ويعاد فحص الصلاحية والاشتراك والتفضيلات قبل الإرسال. لا يعاد إرسال القديم بعد تعديل التفضيلات أو إعادة التفعيل.
- تذكير الاشتراك خلال الثلاثة أيام الأخيرة ورسالة الانتهاء، مع مراعاة التجديدات المتصلة. تذكير المحفوظات في اليوم السابق للموعد المعروف حسب تقويم فلسطين.
- الرسائل تعاد بلغة الحساب وروابطها عند التسليم. لا يُخمن موعد تقديم مفقود.
- مراقبة التسليم من صفحة الإدارة «متابعة تسليم التنبيهات»: حالات وفشل ومحاولات وإعادة طلب المحاولة، وطلبات البوت غير المكتملة. الجداول 10 سجلات مع طلب خادم لكل صفحة.
- تُحذف payloads اتصال البوت بعد المعالجة، وتحذف سجلات inbox الأقدم من 7 أيام. لا تُحفظ أكواد التحقق صريحة في طابور الرسائل أو audit.
- فشل الشبكة بعد قبول Telegram للرسالة قد يترك التسليم غير محسوم؛ الطابور يمنع التكرار المنطقي للأحداث لكنه لا يدّعي ضمان exactly-once لدى مزود خارجي.

## الاستضافة من publish إلى التشغيل

1. أكمل التجربة المحلية ونسخة SQL الاحتياطية وإعدادات الاتصال المعروفة للمشروع.
2. انشر Web وWorker بالطريقة الموثقة في [MANUAL-DEPLOYMENT.md](MANUAL-DEPLOYMENT.md)، وارفع مخرجاتهما كاملة بما فيها الأدوات الموجودة سابقًا.
3. اضبط ملف إعدادات كل مخرج بالقيم الحقيقية وPublicOrigin؛ لا ترفع مفاتيح الإنتاج إلى Git.
4. امنح Web صلاحية مجلد الأدلة وDataProtectionKeys. ملفات PDF المؤقتة وإعداداتها تبقى كما هي.
5. ابدأ Web لتطبيق migration، ثم أعد تشغيل خدمة Worker. تحقق من SQL ومن صفحة الأدوات ومن سجل العامل.
6. فعّل webhook تليجرام بعنوان الموقع HTTPS وسره، واسمح بخروج HTTPS إلى api.telegram.org. افحص التسجيل والرموز وواجهة الهاتف عمليًا.
7. أنشئ باقات تجريبية وصلاحيات واختبر منحًا يدويًا وخصمًا كاملًا ثم التجميد والاستئناف ومراجعة الدفع. لا تفعّل تحصيل أموال قبل اكتمال adapters وفحص المزود الحقيقي.

## فحوص هذه الدفعة وحدودها

- نجح بناء Web/Core/Worker ومشروع الفحوص، وتطابق model مع migration دون الاتصال بـSQL.
- بعد ربط البوابتين وSandbox نجحت 103 حالات عضوية ومسارات HTTP، و34 حالة لحظة و55 حالة جوال باي بمحاكاة الشبكة والتوقيع، و14 حالة ترقيم. في الدفعة السابقة نجحت 56 حالة workflow و14 حالة ترقيم و12 سيناريو عرض Chromium للعربية والإنجليزية.
- `--membership-check`: قواعد ومفاتيح فريدة ومضيف HTTP مؤقت بقوالب Razor الحقيقية؛ لا SQL حي أو بوت أو دفع.
- `--membership-sql-check`: فحص اختياري ينشئ قاعدة مؤقتة باسم عشوائي ثم يحذفها، ويحتاج `HIRING_TEST_SQL` لحساب يملك صلاحية إنشاء قاعدة تجريبية. لم يُشغّل لعدم توفر اتصال اختبار هنا.
- `--workflow-check` و`--admin-pagination-check`: فحوص سير الجمع والتواريخ والترقيم الحالية.
- مراجعة Chromium لعرض الهاتف وسطح المكتب بالعربية والإنجليزية على بيانات fixture؛ ليست اختبارًا لحسابات أو دفعات حقيقية.
- فحص `--source-setup-check` القديم يتوقع رفض HTML فوق مليوني حرف، بينما الكود المرفوع من المستخدم قبل هذه الدفعة يعتمد مسار large-page حتى 16 مليونًا؛ الفحص يفشل عند هذا التعارض الموجود مسبقًا. لم يُغيّر منطق المصادر في هذه الدفعة ولم يُخفَ الفشل بإضعاف الاختبار.
- تطبيق migration والمعاملات المتزامنة على SQL Server، ربط بوت حقيقي، الدفع الحقيقي، Windows/IIS، وسياسة أدلة الهوية والاحتفاظ بمرفقات الدفع ما زالت تحتاج تحققًا قبل إطلاق الميزة للعامة.
