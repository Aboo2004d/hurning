# تجربة تليجرام ولحظة محليًا وعبر الاستضافة

تحديث: 18 أكتوبر 2026. الربط مخصص للاختبار أولًا، ولم تُجر عملية دفع أو إرسال بوت حقيقية في البيئة السحابية.

## ما جُهز

- البوت `PalestineEmploymentBot`؛ الموقع يدعم التسجيل وربط الحساب بالهاتف الخاص بالمستخدم ورمز تليجرام، ثم أوامر الحالة والتفضيلات والتنبيهات والمدفوعات.
- تليجرام يعمل عبر Webhook؛ Web يحفظ التحديث في SQL، وWorker يعالجه ويرسل الرسائل. يجب تشغيل الاثنين.
- لحظة: صفحة دفع مستضافة، إنشاء عملية من السيرفر، والتحقق بواسطة API. لم يُستخدم Inline أو حفظ بطاقة أو خصم دوري.
- اختيار البيئة حسب .NET: Development يختار `Sandbox` مع مفتاح `sk_test_`، وProduction يختار قسم `Production` مع `sk_live_`. راجع PAYMENT-ENVIRONMENTS.md للبيئات وفحوص الأدوات.
- المرجع `hiring-<order GUID without hyphens>` ثابت لكل طلب. قيمة 5 شيكل تُرسل 500 أغورة.
- توقيع `x-lahza-signature` (وفي الطلب الفعلي `X_lahza_signature`) هو HMAC-SHA256 hex على البايتات الأصلية، بمفتاح لحظة السري نفسه. لا يحتاج مفتاح Webhook منفصلًا. مثال C# المرسل من التوثيق يستخدم SHA512 خطأً؛ التنفيذ يتبع نص التوثيق وأمثلة Node/Python، ويحتاج اختبار التوقيع الحقيقي.
- `charge.success` الموقّع يعيد الطلب إلى طابور التحقق المحفوظ بقاعدة البيانات. الرد 200 بعد الحفظ، والتحقق عبر API يتم بالخلفية دون الاعتماد على البوت أو browser callback. لا يضاف اشتراك اعتمادًا على جسم Webhook وحده.
- لا يمنع انتهاء 10 دقائق اعتماد دفع ناجح متأخر. تكرار التأكيد لا يزيد الاشتراك مرتين. تعطيل استقبال مشتريات جديدة من لوحة البوابات لا يمنع التحقق من الطلبات القائمة.
- يحفظ بدء إنشاء العملية قبل الاتصال بلحظة ويمنع تكرار initialization لنفس الطلب؛ رابط checkout الناجح محفوظ لإعادة فتحه ضمن مهلة الطلب. إذا انتهى الاتصال دون استلام الرابط، لا يعاد إنشاء نفس العملية تلقائيًا: تحقق من الطلب/لوحة لحظة أو اطلب المراجعة. لا تبدأ طلبًا آخر قبل معرفة نتيجة السابق.
- لا يوجد Refund تلقائي. أضيف موصل جوال باي لاحقًا حسب عقد الشريك؛ راجع JAWWAL-PAY.md وPAYMENT-ENVIRONMENTS.md.

## الرابط واللغة

أصل التجربة الحالي في ملفي الإعدادات:

```text
https://gusty-attentive-renewed.ngrok-free.dev
```

صفحات المستخدم تبدأ بـ `/ar` أو `/en`. رابط العودة يتضمن `lang` حسب لغة حساب المستخدم وقت إنشاء الدفع، ثم يذهب لصفحة عضو محمية ويتحقق من طلب ذلك العضو فقط. العودة لا تثبت الدفع.

روابط الخدمات ثابتة، دون لغة أو تحويل لتسجيل الدخول:

```text
https://gusty-attentive-renewed.ngrok-free.dev/integrations/telegram
https://gusty-attentive-renewed.ngrok-free.dev/integrations/lahza/webhook
https://gusty-attentive-renewed.ngrok-free.dev/integrations/lahza/return
```

رسائل البوت وروابطه للحساب المرتبط تتبع اللغة المحفوظة في الموقع. شاشة طلب مشاركة الهاتف تستخدم لغة التسجيل. قوائم أوامر البوت تسجّل بالعربية افتراضيًا و`ar`، وبالإنجليزية `en`؛ Telegram يختار لغة قائمة الأوامر بحسب إعدادات تطبيقه. النصوص والروابط للحساب تتبع لغة الموقع. أخطاء الربط قبل التعرف على الحساب قد تظهر باللغتين.

## التحضير قبل وضع الرموز

1. جهّز SQL Server وملف الاتصال المعتاد. احتفظ بنسخة احتياطية لقاعدة التجربة.
2. حدّث الكود وابنِ المشروع. أضيفت Migration باسم `LahzaHostedCheckout` لحقلي `CheckoutStartedAt` و`CheckoutUrl`. بدء Web يطبقها وفق آلية المشروع الحالية. لا تتراجع عن هذه Migration بعد وجود عمليات checkout؛ يمنع Down حذف دليل بدء العملية.
3. أبقِ الرموز `***` أثناء التحضير؛ `Enabled=true` في JSON لا يكفي لتشغيل المزود حتى تكتمل بياناته. لا تظهر لحظة للمستخدم حتى تفعيلها من لوحة الإدارة أيضًا.
4. شغّل الموقع محليًا بواسطة `scripts/start-local.ps1` ثم النفق في نافذة مستقلة:

```powershell
ngrok http 5186
```

5. جرّب فتح `/ar` و`/en` عبر النفق. إن تغيّر دومين ngrok، حدّث `Seo:PublicOrigin` و`Payments:Lahza:Sandbox:PublicOrigin` (وفي النشر `Payments:Lahza:Production:PublicOrigin`) في ملفي Web وWorker، ثم أعد التشغيل وتسجيل Webhooks. يجب أن يصل النفق إلى Web وليس Worker. لا تعرض SQL أو خدمات الأدوات عبر النفق.

## آخر خطوة إعداد: استبدال الرموز محليًا

في `src/HiringPs.Web/appsettings.json` و`src/HiringPs.Worker/appsettings.json`، ضع القيم نفسها:

- `Telegram:BotToken`: من BotFather.
- `Telegram:WebhookSecret`: قيمة عشوائية مشتركة من 32 حرفًا أو أكثر، حروف إنجليزية وأرقام أو `_` و`-`، وبحد أقصى 256.
- `Payments:Lahza:Sandbox:SecretKey`: مفتاح **Test** من لوحة لحظة.

لا نحتاج PublicKey لصفحة الدفع المستضافة. لا ترسل المفاتيح في المحادثة، ولا تحفظ القيم الحقيقية في commit. الإعدادات تقرأ JSON بالطريقة التقليدية دون user-secrets. بعد أي تعديل أوقف العمليات بالسكربت ثم أعد التشغيل كي تُنسخ إعدادات Worker إلى ناتج البناء أيضًا.

```powershell
.\scripts\stop-local.ps1
.\scripts\start-local.ps1
.\scripts\configure-integrations.ps1 -Telegram
```

السكربت يقرأ ملفات الإعدادات، يطابق Web وWorker، ويتحقق من هوية البوت، ويسجل Webhook مع `secret_token` وأوامر واسم ووصف بالعربية والإنجليزية دون طباعة الرموز. لا يحذف تحديثات Telegram المعلقة. نجاح تسجيل Webhook لا يثبت سلامة SQL/Worker؛ أكمل الاختبارات التالية.

## تجربة تليجرام أولًا

1. افتح `/ar/Registration` وسجّل برقم الهاتف المرتبط بتليجرام بصيغته الدولية وبريدك وكلمة مرورك.
2. افتح زر البوت من صفحة التسجيل؛ لا يكفي إرسال `/start` عادي لتفعيل حساب غير مربوط.
3. شارك رقمك من زر البوت، ثم أدخل رمز التحقق في الموقع خلال 5 دقائق. النص اليدوي أو جهة اتصال لشخص آخر مرفوضان.
4. جرّب `/status` و`/help`. بدّل لغة الموقع إلى الإنجليزية أثناء الدخول، ثم أعد `/status`؛ النص والروابط يجب أن تصبح إنجليزية.
5. جرّب `/stop` وإعادة التنبيهات من إعدادات العضو برمز جديد، واستعادة كلمة المرور. عند تعطل الإرسال راجع Worker وTelegram `getWebhookInfo`؛ لا تنشر رابط Bot API الذي يتضمن Token في سجل عام.

## تجربة لحظة بعد نجاح تليجرام

1. في لوحة لحظة **Test**، أضف Webhook URL المذكور أعلاه. رابط العودة يرسله التطبيق لكل عملية؛ إن طلبت اللوحة Callback افتراضيًا ضع `/integrations/lahza/return` على أصل النفق.
2. اضبط مهلة حساب لحظة مرة واحدة، الحساب مخصص لهذا الموقع وفق الاتفاق:

```powershell
.\scripts\configure-integrations.ps1 -LahzaSession
```

يرسل السكربت `PUT /payment_session_timeout` بقيمة `timeout=600` ثم يتحقق منها بـGET. هذا إعداد عام للحساب، وليس تغييرًا مع كل عملية.

3. افتح الإدارة ← الباقات: أنشئ باقة تجريبية وحدد مدة/حقوق التفاصيل والتنبيهات، ثم الإدارة ← بوابات الدفع: فعّل Lahza. السعر والمدة يبقيان من إدارة الموقع، ولا تُرسل خطة تجديد دوري إلى لحظة.
4. ادخل بعضو مفعل، ثم «باقتي» ← العرض ← مراجعة السعر والخصم وشروط عدم الاسترداد ← إنشاء الطلب ← إتمام الدفع.
5. استخدم بيانات الاختبار الرسمية من حساب لحظة، لا بطاقة حقيقية. بعد العودة يجب التحقق عبر API ثم عرض حالة الطلب والاشتراك. إن لم يتم التحقق فورًا، زر التحقق متاح مع حد 30 ثانية، والعامل يعيد فحص الطلبات المعلقة دوريًا.
6. تحقق من اسم الباقة/المبلغ/التاريخ ورسالة تأكيد البوت. جرّب `/payment_status <orderId>` لطلبك. طلب مستخدم آخر يجب ألا يُعرض أو يُعدّل.
7. جرّب الفشل، إغلاق صفحة الدفع، إعادة فتح الطلب، تأخر وصول Webhook، تكراره، وصول نجاح بعد مهلة الطلب، التجديد مع أيام متبقية، الخصم الكامل والمراجعة اليدوية. لا يجب منح مدة مرتين لنفس الطلب. تحقق كذلك من ظهور الطلب عبر `/en`.

## الاستضافة

- استبدل أصل ngrok بأصل الموقع HTTPS في **Web وWorker**، وارفع مخرجات نشر المشروعين مع إعداداتهما الصحيحة، وحافظ على SQL ومجلد أدلة الدفع الدائم.
- شغّل Worker كخدمة دائمة، وليس عند زيارة صفحة. اجعل مسارات integrations عامة لكن تحميها التواقيع؛ لا تمررها عبر صفحات تسجيل الدخول أو تحدي متصفح.
- الإنتاج منفصل: قسم Production ومفتاح Live وربط Webhook الخاص به وتسجيل أوامر البوت على العنوان الجديد. لا تخلط مفاتيح Test/Live؛ مفتاح البيئة المختارة يحدد اتصال التحقق. حقل domain اختياري في الرد الفعلي: يقبل غيابه أو فراغه، وتُرفض أي قيمة صريحة لا تطابق test/live للبيئة. إعداد مهلة الإنتاج راجعه في لوحة لحظة؛ سكربت الضبط المحلي متعمدًا يسمح Test فقط.
- لا تُعد نجاح البناء أو المحاكاة إثباتًا لخصم فعلي أو توقيع حي أو عمل استضافة Windows/IIS. يجب إتمام التجارب السابقة قبل إتاحة الاشتراكات الحقيقية.

## التحقق المنفذ في هذه الدفعة

نجح بناء الحل ومشروع الفحوص، و101 فحص عضوية وHTTP (منها روابط العودة العربية والإنجليزية ورفض Webhooks بمفاتيح غير مهيأة)، و34 فحص لحظة بمحاكاة HTTP وتوقيع معروف. تطابق نموذج EF مع Snapshot وولّد SQL الإضافة؛ لم يطبق على SQL حي. سكربت PowerShell مكتوب للتشغيل على جهاز المستخدم؛ لم يُنفذ على Windows هنا، ولم تسجّل الخدمات الخارجية أو تُختبر مفاتيح حقيقية.


اختيار البيئة الحالي والمفاتيح وفحص لحظة وجوال باي من الأدوات موضح بالتفصيل في [PAYMENT-ENVIRONMENTS.md](PAYMENT-ENVIRONMENTS.md). ملفا الإعدادات يحتويان القسمين؛ لم يعد TestMode إعداد تشغيل.

## تسجيل Webhook من لوحة الإدارة

يمكن تسجيل استقبال أوامر البوت دون PowerShell من **المحتوى والتواصل ← ربط
بوت التليجرام** أو من الرابط الموجود في صفحة قنوات التليجرام. الصفحة تفحص
getMe وgetWebhookInfo تلقائيًا، وتعرض اسم البوت والعنوان المطلوب والعنوان
المسجل والتحديثات المعلقة وآخر خطأ توصيل بتوقيت فلسطين. التسجيل إجراء POST
صريح للمسؤول ومحمي بـantiforgery، ولا يجري تلقائيًا عند تشغيل الموقع.

الزر يستعمل إعدادات Web الفعلية، بما فيها إعدادات البيئة ومتغيراتها، ويعتمد
`Seo:PublicOrigin` لتسجيل `/integrations/telegram` عبر HTTPS. يتحقق من هوية
البوت أولًا ثم يرسل سر التحقق وallowed_updates=message مع
`drop_pending_updates=false`، ويعيد قراءة الحالة للتحقق من العنوان. لا يعرض
المفاتيح ولا يحفظها في سجل العمليات. إعادة التسجيل تحدث السر حتى إذا لم
يتغير العنوان؛ getWebhookInfo لا يكشف السر الحالي ولا يمكن مقارنته من الواجهة.
لا يلزم تطابق ملف Worker عند استخدام الويب والعامل المضمّن. السكربت القديم
ما زال متاحًا لمن يستخدم طريقة الإعداد القديمة، لكن هذه الصفحة لا تعتمد عليه.

نجاح تسجيل العنوان لا يثبت وصول تحديث أو معالجته أو إرسال تنبيه. قد يبقى آخر
خطأ توصيل لدى Telegram ظاهرًا بعد زواله. اختبر أمرًا جديدًا بعد التسجيل وراجع
TelegramInbox وسجل العمليات. الإرسال التجريبي للقنوات يستخدم Bot API في الاتجاه
المعاكس ولا يحتاج Webhook، لذلك قد ينجح حتى قبل تسجيل استقبال أوامر البوت.
لا ترسل هذه الصفحة أي رسالة ولا تغير قوائم الأوامر أو ملف البوت الشخصي.

التحقق المحلي يستخدم HTTP وهميًا فقط، ويغطي الهوية والتسجيل والاحتفاظ بالتحديثات
وحجب المفاتيح والأخطاء والصلاحيات وسجل العمليات. اختبارات الواجهة تعمل على
صفحة معاينة ببيانات مصطنعة؛ لم يتم تسجيل Webhook حقيقي أثناء التطوير.
